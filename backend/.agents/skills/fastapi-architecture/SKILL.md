# Архитектура FastAPI

Используй структуру ниже как ориентир для нового проекта. Создавай только нужные задаче модули.

```text
app/
├── __main__.py           # create_app, lifespan, запуск
├── context.py            # AppContext, сборка клиентов и сервисов, ContextDep
├── api/
│   ├── __init__.py       # регистрация роутеров
│   ├── dependencies.py  # общие Depends, SessionDep
│   └── <resource>/
│       ├── routes.py    # APIRouter и HTTP-обработчики
│       └── schemas.py   # Pydantic-модели запросов и ответов
├── services/             # бизнес-правила и сценарии
├── db/
│   ├── models/          # SQLAlchemy-модели
│   ├── crud/            # классы доступа к БД по сущностям
│   ├── session/         # engine, фабрика сессий, get_session
│   └── alembic/         # миграции
├── clients/               # внешние API и хранилища
├── config/               # настройки из окружения
├── cache/                # кэширование, если требуется
├── telemetry/            # логи, метрики, middleware
└── utils/                # небольшие функции без бизнес-логики
```

- **API:** валидируй вход через схемы, объявляй модель ответа и HTTP-статус. Обработчик принимает запрос, вызывает нужную операцию и формирует ответ. Новый роутер подключай через общий реестр.
- **Слои:** SQL размещай в `db/crud`, внешние вызовы — в `clients`, бизнес-правила и многошаговые операции — в `services`. Простой обработчик может вызвать CRUD напрямую; сервис нужен для содержательной логики, а не для пересылки аргументов.
- **CRUD:** оформляй доступ к данным классами по сущностям, например `ProductCRUD`. Передавай `AsyncSession` в конструктор, запросы реализуй методами экземпляра. Не создавай общий базовый CRUD-класс без необходимости.
- **Сервисы:** оформляй содержательные бизнес-сценарии классами. Передавай CRUD, клиенты и другие необходимые зависимости через конструктор; собирай сервис для запроса с одной `AsyncSession`. Чистые вычисления и проверки оставляй функциями. Простой обработчик может обращаться к CRUD напрямую, если бизнес-логики нет.
- **Типизация:** используй аннотации для параметров, результатов и известных структур, передаваемых между слоями. Для таких структур выбирай `TypedDict` или `dataclass`, для подменяемых интерфейсов — `Protocol`, когда это полезно. Для динамического JSON и конфигурации не придумывай жёсткую схему: проверяй данные на границе и используй подходящие общие типы.
- **Зависимости:** в новом проекте определи `get_session` и алиас `SessionDep = Annotated[AsyncSession, Depends(get_session)]`. Если нужен общий контекст, создай `AppContext`, `get_app_context` и `ContextDep = Annotated[AppContext, Depends(get_app_context)]`. Сервисы получают нужные объекты явно. `db` и `clients` не должны зависеть от `api`; HTTP-ошибки преобразуй на границе API.
- **Ресурсы:** собирай приложение в `create_app`, управляй общими клиентами и пулом БД через `lifespan`, закрывай их при остановке. Сессию выдавай на запрос, не храни общую изменяемую сессию в контексте приложения.
- **Транзакции:** задавай границу транзакции на уровне целой операции, не вызывай `commit` внутри CRUD-методов. Несколько связанных записей должны сохраняться атомарно; при ошибке обеспечь rollback. Транзакция БД не откатывает внешние вызовы — учитывай частичный успех.
- **Модели:** разделяй HTTP-схемы и ORM-модели. Изменения структуры БД оформляй миграциями; подключай новые модели к общей metadata по принятому в проекте способу.
- **Асинхронность:** используй асинхронный I/O; блокирующие SDK и тяжёлые вычисления выноси из event loop в подходящий поток, процесс или существующий исполнитель.
- **Доступ и конфигурация:** проверяй права и принадлежность связанных ресурсов до чтения или изменения. Переданный клиентом `user_id` сам по себе не подтверждает личность. Настройки и секреты получай через конфигурацию, не раскрывай их в ответах и логах.

Не добавляй repository, unit-of-work, базовые сервисы или новые слои без конкретной необходимости. При изменениях сохраняй публичные контракты и возможность подменить зависимости в тестах.
