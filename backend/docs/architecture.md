# Архитектура

Backend работает как одно приложение на Python 3.12 и FastAPI. Каталог, профили, рекомендации, карты, избранное и демонстрационные покупки объединены в нем. Данные хранятся в PostgreSQL 16. Рекомендательная система выполняется внутри backend, а для генерации пояснений используется внешний API Cloudflare Workers AI.

## 1. Общая организация

Система использует клиент-серверную архитектуру. Frontend на React и TypeScript отвечает за интерфейс, backend предоставляет REST API и выполняет прикладные операции. Доступ к базе данных и внешней модели проходит через сервер.

Backend организован как модульный монолит. HTTP-обработчики, бизнес-логика, работа с данными и рекомендательные алгоритмы разделены по ответственности, но запускаются в одном приложении. Такое устройство позволяет согласованно обновлять пользовательское состояние без обмена между отдельными сервисами.

## 2. Компоненты и ответственность

| Компонент | Назначение |
| --- | --- |
| Frontend | Показывает витрину, карточки и личный кабинет, принимает ответы анкеты и действия пользователя |
| HTTP API | Принимает запросы, проверяет их формат, выполняет авторизацию и возвращает ответы в JSON |
| Прикладные сервисы | Управляют профилями, каталогом, подборками, картами, избранным и правами доступа |
| RecSys | Оценивает соответствие материалов задаче пользователя и определяет состав и порядок выдачи |
| LLM-клиент | Передает разрешенный контекст во внешнюю модель и проверяет полученные пояснения |
| Слой доступа к данным | Читает и изменяет состояние через SQLAlchemy и асинхронные сессии PostgreSQL |
| PostgreSQL | Хранит каталог, пользовательское состояние, результаты подбора и сохраненные пояснения |

Frontend обращается к API по HTTP. Персональные операции используют JWT Bearer-токен. Сервер проверяет принадлежность данных пользователю и условия доступа к материалам независимо от состояния интерфейса.

## 3. Обработка пользовательских сценариев

### Персональная подборка и карта

1. Frontend передает параметры анкеты и выбранный режим обучения.
2. Backend проверяет значения и собирает контекст из текущих предпочтений и доступных материалов.
3. RecSys ранжирует кандидатов. При формировании карты дополнительно учитываются роль материала и последовательность изучения темы.
4. Сервер формирует карточки с условиями доступа и пояснениями. При включенной генерации выбранные материалы могут получить текст от LLM.
5. API возвращает подборку или карту для отображения. Сохранение результата выполняется отдельной пользовательской операцией.

Ранжирование сочетает текстовые признаки TF-IDF и правила соответствия задаче бизнеса. Для последовательного обучения используются подготовленные маршруты и проверки состава карты. При недостатке данных применяются базовые правила подбора; режим популярности не требует персонального профиля и вызова LLM.

### Пояснение к материалу

Backend передает модели факты материала и доступный контекст предпочтений. Отдельный запрос персонального пояснения требует авторизации. Полученный текст проходит проверку формата и сохраняется с привязкой к пользователю, материалу и контексту генерации.

При повторном обращении сервер может использовать сохраненное пояснение. Изменение профиля или исходных сведений о материале учитывается при проверке его актуальности. Это сокращает повторные обращения к внешней модели.

### Сохранение пользовательского состояния

Избранное, сохраненные карты и права доступа связаны с учетной записью. Отметки изучения хранятся отдельно от состава карты: изменение подборки не сбрасывает отметку материала. Операции с подписками и покупками проверяются сервером и обновляют демонстрационные права доступа в базе данных.

## 4. Данные, безопасность и устойчивость

Курсы, статьи и документы приводятся к общему представлению каталога. Профиль содержит явные ответы пользователя; состояние обучения хранится отдельно от описаний материалов. Для работы с БД используются асинхронные сессии, изменения в рамках бизнес-операции объединяются транзакцией. Структура БД обновляется миграциями Alembic.

Ключ Cloudflare остается на сервере. Пароли, email и содержимое закрытых уроков не передаются в запросы модели. Решения о доступе, составе рекомендаций и демонстрационных покупках принимаются прикладной логикой.

Ожидание внешней генерации ограничено по времени. При ошибке или недоступности модели используются подготовленные тексты и шаблоны. Проверки ответа помогают отсеивать некорректный текст, но не заменяют оценку его достоверности.

## 5. Основные папки проекта

| Папка | Содержимое |
| --- | --- |
| `frontend/src` | Страницы, компоненты интерфейса и обращения к API |
| `backend/src/api` | HTTP-маршруты, схемы запросов и ответов |
| `backend/src/services` | Прикладная логика и взаимодействие компонентов |
| `backend/src/db` | Модели, операции с БД и миграции |
| `backend/src/ml` | Алгоритмы рекомендаций и подготовленные данные |
| `backend/src/clients` | Подключение внешней LLM |
| `backend/src/config` | Настройки, справочники и конфигурация демоданных |
| `backend/docs` | Описание решения, архитектуры и API |

## 6. Конфигурация и развертывание

Параметры backend задаются переменными окружения. Docker Compose поднимает PostgreSQL, применяет миграции и запускает API. Данные БД сохраняются в постоянном томе. Frontend собирается с помощью Vite.

Внешняя генерация включается отдельно; для запуска backend ключ модели не обязателен. HTTP-контракт описан в OpenAPI, интерактивная документация доступна через Swagger UI.
