# Mistral: клиент описаний

Единственная модель — `@cf/mistralai/mistral-small-3.1-24b-instruct`, API Cloudflare Workers AI.
Все команды выполняются из папки `backend`. Клиент подключается к рекомендациям через адаптер при `LLM_ENABLED=true`.

При `poetry install` зависимости клиента устанавливаются вместе с backend.
Для отдельного запуска клиента достаточно:

```cmd
python -m pip install -r src/clients/requirements.txt
```

Скопировать переменные `CLOUDFLARE_*` и `LLM_*` из `.env.example` в `.env` и заполнить
токен и Account ID. Существующий `.env` не перезаписывать. Настройки читаются при
создании клиента, окружение имеет приоритет. `LLM_MODEL` допускает только Mistral;
другая модель отклоняется при загрузке настроек. Аргумент `model` из функций генерации удалён.

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `LLM_MODEL` | `@cf/mistralai/mistral-small-3.1-24b-instruct` | Фиксированная модель |
| `LLM_TIMEOUT_SECONDS` | `30` | Таймаут запроса, секунды; в backend ограничен общим `GENERATION_TIMEOUT_SECONDS` |
| `LLM_MAX_TOKENS` | `1024` | Максимум токенов ответа, поле API `max_tokens` |
| `LLM_TEMPERATURE` | `0.4` | Вариативность генерации |

```python
from src.clients.llm import LLMClient

async with LLMClient() as client:
    result = await client.generate_course_description(material, profile, is_studied=False)
    print(result.text, result.status)
    print(client.get_usage())
```

`material` — загруженный `db.models.materials.Materials` или `MaterialInput`.
`profile` — загруженный `UserProfiles` или `ProfileInput`, необязателен.
Клиент не читает БД, не сохраняет результаты и не обращается к lazy relationships.
Поля берутся только из явного белого списка. `metadata`, приватные уроки, email,
пароли и идентификатор пользователя в API не передаются. Значения кодов профиля
не расшифровываются моделью самостоятельно. Подписи подставляются из соответствующей
версии `src/config/demo/v*.json`; при неизвестной версии или коде подпись не добавляется.

`is_studied` вычисляется вызывающим backend по актуальной таблице
`mvp.user_material_studies` для текущей пары `(user_id, material_id)`:
есть запись — `True`, нет — `False`, запрос не выполнялся — `None`.
Таблицей управляет команда backend; модуль LLM не создаёт таблицу и не содержит
её ORM-модель или миграцию. Интеграция рекомендаций пока не передаёт отметки и историю в LLM.
Это текущая отметка пользователя, а не доказательство усвоения навыков.
Она не добавляется в `Materials`, снимок карты или результат генерации.

Полный ответ проверяется на корректную оболочку, завершённость, пустоту, длину
и отсутствие HTML. Достоверность всех формулировок автоматически не гарантируется.
Frontend должен показывать результат как текст, а не исполнять HTML.
При сбое возвращается непустой `default_offer_text` материала (`fallback`), а при его
отсутствии — исходная аннотация `public_description`. Без непустого `public_description`
запрос к модели не отправляется: подготовленный текст возвращается со статусом
`fallback`; если его тоже нет — `status=failed`, `text=null`. Для документа запрос может
использовать только название при отсутствии описания. В обоих случаях для статьи или курса
`error=missing_public_description`. Поле `default_offer_text` читается из ORM/MaterialInput,
но не передаётся модели, в том числе в истории изученных материалов.
Автоматических повторов и платных переключений нет. Ввод вне схемы вызывает ошибку
валидации до запроса. Streaming и траектории в этом модуле не реализованы.

`check_status()` проверяет только доступ к каталогу моделей аккаунта (Workers AI Read).
Успех не подтверждает право запуска конкретной модели или остаток квоты.
`get_usage()` показывает только известный расход этого экземпляра с момента создания;
неизвестные остатки аккаунта — `None`. Другие процессы не учитываются.

Unit-тесты клиента (без сети, БД и ключей):

```cmd
python -m pip install pytest
python -m pytest src/clients/test_llm.py -q --tb=short
```

Они также входят в общий запуск `poetry run pytest -q --tb=short`.

Ручные проверки Mistral расходуют квоту. Качество текста оценивается вручную.
Пять отдельных примеров (4 реальных запроса; пример без аннотации отклоняется локально):

```cmd
python -m src.clients.check_mistral
```

Выводятся синтетические входные данные, ответ обычным текстом, время в секундах,
статус, ошибка и расход. При `fallback` выводится резервная аннотация, не ответ модели.
Настройки и ключ берутся из `.env`; модель для этого запуска всегда Mistral.

Сравнение одного курса с восемью комбинациями профиля и истории изучения (8 запросов):

```cmd
python -m src.clients.check_mistral --profiles
```

Пять смешанных сочетаний материалов, профилей и истории (4 запроса):

```cmd
python -m src.clients.check_mistral --mixed
```

Проверяются статьи и курсы, платный и бесплатный доступ, разные цели и режимы обучения,
изученный материал, связанные и несвязанные темы, неполный профиль, отсутствие аннотации.
Отрасль `demo` взята из тестового справочника. Вариант с `unknown_test` и пустой аннотацией
отклоняется до API. Метаданные prerequisites/outcomes/evidence не передаются.
Ожидаемый отказ для пустой аннотации не считается провалом проверки: код выхода 0.
Сбой API или некорректный ответ для материала с аннотацией даёт код выхода 1, даже при `fallback`.

Используются синтетические профили с кодами из `src/config/demo/v1.json`: без профиля,
краткая подача, практика, повторение изученного, последовательное обучение и неполный профиль;
ещё два случая проверяют влияние связанного предыдущего материала и материала на другую тему.
Стадия бизнеса не означает уровень навыков. Подписи стадии, отрасли и цели из конфигурации
передаются для персонализации вместе с `learning_mode` и отметкой `is_studied`.
Необязательный `studied_materials` принимает до 10 объектов `Materials`/`MaterialInput`
или словарей с названием `title` и типом `kind`.
Вызывающий код может передать разрешённые описания истории; клиент сам не читает БД.
Интеграция рекомендаций историю пока не передаёт. Текущий материал исключается из истории.
Профиль и история служат скрытым контекстом для выбора акцентов в подтверждённых темах.
Описание не ссылается на профиль, изученные материалы, отметки или поля входных данных.
Программа и изучаемые навыки берутся из описания текущего материала. Допустимо объяснять
логичную практическую пользу, например применение таблиц для учёта, без обещания результата.
Нельзя добавлять фактические свойства: реальные кейсы, сертификаты или неподтверждённые темы.
Без аннотации статьи или курса генерация не выполняется; при наличии возвращается подготовленное описание.
История учитывается лишь при явном пересечении описаний и не доказывает владение навыками.
Справочник `config.skills` не является свидетельством освоения навыков пользователем.

```python
result_json = await client.generate_description_json(
    material, profile, studied_materials=studied_materials, is_studied=False,
)
```

Из материала дополнительно передаются `learning_role`, `annotation_source`, `annotation_version`.
Они читаются из существующих ORM-полей, включая материалы истории; новых таблиц нет.
Адаптер передаёт названия тем, тегов и отраслей, режим и подтверждённые тематические совпадения
только выбранных материалов. Отсутствующие данные пропускаются. `metadata` (включая
prerequisites/outcomes/evidence), история, цены и личные идентификаторы не передаются.

Клиент использует `/ai/run/` и извлекает текст из `result.response` Workers AI.
Идентификатор модели и расход сохраняются в `DescriptionResult`; в текст описания они не попадают.
